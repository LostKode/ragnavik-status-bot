# Player connection status

`GET /connection-status` is an unauthenticated, read-only, no-store response for the client error dialog. Expose only this exact GET route through an HTTPS reverse proxy on the application host (Quetzalcoatl); keep the control API private. No game-server restart is required to deploy this service change. Configure the UI's `[Ragnavik Connection] Status Endpoint` to the public HTTPS URL when the route is deployed. The endpoint is intentionally unset in the UI until hosting is configured.

The response has schemaVersion 1, state (`online`, `maintenance`, `unavailable`, or `unknown`), requiredClientVersion, lastVerifiedClientVersion, and checkedAt (Unix seconds). It never includes addresses, player identities, maintenance free text, or control credentials. Public requests read the latest background observation rather than running expensive game probes. Observations older than 120 seconds produce unknown status with no current version. HTTP/proxy caching must remain disabled.

After an authorized game deployment has passed readiness, loaded-mod, anti-cheat, and client/server parity checks, POST to the private `/deployment/verified` route using the existing `X-Ragnavik-Control` authentication. The JSON body is `{"container":"<current container ID, at least 12 hex characters>","requiredClientVersion":"<verified matching Client Pack x.y.z>"}`. This is an operator attestation of completed verification, not automatic validation of package contents. Never fill it from the package catalog or latest changelog. The endpoint checks that this container is currently healthy and matches the ready hook, returning 409 for a mismatch and 204 on success.

A new ready hook invalidates the current-version attestation, including an internal restart of the same container. Repeat verification and registration after recovery. The last verified version remains available with an explicit historical label while the current requirement is unknown. A new public client release never changes either deployed-version field. A failed update therefore cannot advertise its target version as active. After registration the next background sample refreshes availability, normally within 30 seconds.

Activation order: deploy this status-service branch; expose the exact HTTPS GET route; verify and register the currently running server's matching Client Pack; configure the UI endpoint in the coordinated client release. Do not publish the UI expecting verified version notices before these steps are complete. Test-mode UI never requests this endpoint.
